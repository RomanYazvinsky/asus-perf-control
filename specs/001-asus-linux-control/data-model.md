# Data Model: ASUS Linux Control Tool

**Feature**: 001-asus-linux-control  
**Date**: 2026-04-08  
**Input**: spec.md Key Entities section

## Overview

This document defines the core data structures used throughout the ASUS Linux Control Tool. All entities are derived from functional requirements and are technology-agnostic (no Rust/Dart implementation details).

---

## Core Entities

### 1. Performance Profile

**Description**: Represents a complete system configuration snapshot that can be saved, loaded, and applied.

**Attributes**:
- `name`: string - User-friendly profile name (e.g., "Gaming", "Battery Saver", "Work")
- `thermal_policy`: integer (0-2) - Performance mode (Silent=0, Balanced=1, Turbo=2)
- `gpu_mode`: enum - GPU power mode (Eco, Standard, Ultimate)
- `fan_curve_id`: string (optional) - Reference to associated fan curve
- `charge_limit`: integer (0-100, optional) - Battery charge threshold percentage
- `display_refresh_rate`: integer (optional) - Screen refresh rate in Hz
- `sustained_tdp_w`: integer (optional) - Custom sustained TDP in watts; null = use mode default
- `boost_tdp_w`: integer (optional) - Custom boost TDP in watts; null = use mode default
- `cpu_temp_limit_c`: integer (optional) - Custom CPU thermal ceiling in °C; null = use mode default
- `created_at`: timestamp - Profile creation time
- `is_default`: boolean - Whether this is the default profile

**Relationships**:
- Has one Fan Curve (optional)
- Used by Automation Rules (many)

**Validation Rules**:
- `thermal_policy` must be 0, 1, or 2
- `charge_limit` must be 0-100 if present
- `name` must be unique per user
- `display_refresh_rate` must match hardware capabilities

**State Transitions**:
- Created → Saved → Applied → Active
- Active profile can be switched to another profile

---

### 2. Sensor Reading

**Description**: Real-time hardware monitoring snapshot taken at a specific timestamp.

**Attributes**:
- `timestamp`: integer (Unix epoch milliseconds)
- `cpu_temp`: float (optional) - CPU temperature in Celsius
- `gpu_temp`: float (optional) - GPU temperature in Celsius
- `fan_speeds`: array of integers - Fan RPM readings (empty array if no fans detected)
- `battery_percentage`: float (optional) - Battery charge level 0-100
- `battery_state`: enum (optional) - Charging, Discharging, Full, Empty, Unknown

**Relationships**:
- Standalone entity, no persistent relationships
- Generated by Sensor Monitor
- Consumed by UI for display

**Validation Rules**:
- `timestamp` must be valid Unix epoch
- `cpu_temp` range: -50 to 120°C (safety bounds)
- `gpu_temp` range: 0 to 120°C
- `fan_speeds` must all be non-negative
- `battery_percentage` must be 0-100 if present

**Refresh Rate**: 1 Hz (one reading per second)

---

### 3. Fan Curve

**Description**: Temperature-to-PWM mapping that controls fan speed based on component temperature.

**Attributes**:
- `id`: string (UUID) - Unique identifier
- `name`: string - User-friendly curve name
- `curve_points`: array of (temperature, pwm_percent) tuples
  - `temperature`: integer (Celsius, 0-100)
  - `pwm_percent`: integer (0-100)
- `min_safe_speed`: integer (0-100) - Minimum PWM % at any temperature
- `max_temp_threshold`: integer (Celsius) - Temperature above which fan must be at max
- `is_preset`: boolean - True for system presets (Silent, Balanced, Performance)
- `created_at`: timestamp

**Relationships**:
- Used by Performance Profiles (one-to-many)
- References Component Temperature (cpu_temp or gpu_temp from Sensor Reading)

**Validation Rules**:
- `curve_points` must have at least 2 points
- Points must be sorted by temperature (ascending)
- PWM must be monotonically increasing with temperature
- Safety rule: If temperature > 80°C, pwm_percent must be >= 30%
- Safety rule: If temperature >= `max_temp_threshold`, pwm_percent must be 100%
- `min_safe_speed` must be <= all pwm_percent values

**Presets**:
- Silent: Quiet operation, lower fan speeds (e.g., 30% at 60°C, 60% at 80°C)
- Balanced: Moderate cooling (e.g., 40% at 60°C, 80% at 80°C)
- Performance: Aggressive cooling (e.g., 60% at 60°C, 100% at 75°C)

---

### 4. Hardware Configuration

**Description**: Detected laptop capabilities and available hardware features.

**Attributes**:
- `model_name`: string - ASUS laptop model (e.g., "ROG Zephyrus G14 GA402")
- `has_anime_matrix`: boolean - Anime Matrix display present
- `has_dgpu`: boolean - Discrete GPU present (Nvidia or AMD)
- `gpu_vendor`: enum (optional) - Nvidia, AMD, or null
- `supported_refresh_rates`: array of integers - Available display refresh rates in Hz
- `fan_count`: integer - Number of controllable fans (0-3)
- `sensor_count`: integer - Number of available temperature sensors
- `supports_charge_limit`: boolean - Battery charge threshold supported
- `supports_dgpu_toggle`: boolean - dGPU disable/enable supported
- `kernel_version`: string - Linux kernel version
- `detected_at`: timestamp

**Relationships**:
- Singleton per application instance
- Read-only after initial detection
- Determines which features are available in UI

**Validation Rules**:
- `fan_count` must be 0-3
- `sensor_count` must be >= 0
- `supported_refresh_rates` must contain at least one value if display control available

**Detection Logic**:
- Check `/sys/class/platform/asus-nb-wmi/` for available interfaces
- Enumerate `/sys/class/hwmon/` for sensors and fans
- Query USB devices for Anime Matrix (VID: 0x0b05)
- Detect GPU via PCI enumeration or NVML/DRM

---

### 5. Automation Rule

**Description**: Conditional trigger that automatically changes system settings based on events.

**Attributes**:
- `id`: string (UUID) - Unique identifier
- `name`: string - User-friendly rule name
- `trigger_condition`: enum - AC_Connected, Battery_Connected, Temperature_Threshold
- `target_profile_id`: string (optional) - Performance Profile to apply
- `target_setting`: object (optional) - Specific setting to change (e.g., `{gpu_mode: "Eco"}`)
- `threshold_value`: float (optional) - Numeric threshold for temperature triggers
- `enabled`: boolean - Whether rule is active
- `priority`: integer - Execution order when multiple rules match (1-100, lower = higher priority)
- `created_at`: timestamp

**Relationships**:
- References Performance Profile (optional, one-to-one)
- Multiple rules can reference the same profile

**Validation Rules**:
- Must have either `target_profile_id` OR `target_setting`, not both
- If `trigger_condition` is Temperature_Threshold, `threshold_value` is required
- `priority` must be 1-100
- `name` must be unique per user

**Trigger Types**:
1. **AC_Connected**: Fires when AC power plugged in
2. **Battery_Connected**: Fires when switched to battery power
3. **Temperature_Threshold**: Fires when CPU/GPU exceeds threshold

**Example Rules**:
- "Power Saving": When Battery_Connected → Apply "Battery Saver" profile
- "Gaming Mode": When AC_Connected → Apply "Gaming" profile  
- "Emergency Cooling": When Temperature_Threshold(85°C) → Set fan curve to "Performance"

---

### 6. App Configuration

**Description**: Application-wide settings and preferences persisted to disk.

**Attributes**:
- `performance`: PerformanceConfig object
  - `default_profile_id`: string - Profile to load on startup
  - `ac_profile_id`: string (optional) - Auto-switch profile when on AC
  - `battery_profile_id`: string (optional) - Auto-switch profile on battery
- `battery`: BatteryConfig object
  - `charge_limit`: integer (0-100, optional)
  - `show_percentage`: boolean
  - `show_time_remaining`: boolean
- `fan_curves`: array of Fan Curve objects
- `automation`: AutomationConfig object
  - `auto_performance_switching`: boolean
  - `auto_gpu_switching`: boolean
  - `auto_refresh_rate`: boolean
  - `backlight_timeout_battery`: integer (optional, seconds)
- `ui`: UIConfig object
  - `theme`: enum (Light, Dark, System)
  - `start_minimized`: boolean
  - `show_tray_icon`: boolean
  - `update_check_enabled`: boolean
- `version`: string - Config schema version for migration

**Relationships**:
- References Performance Profiles by ID
- Contains Fan Curves as embedded objects
- Singleton per user

**Validation Rules**:
- `charge_limit` must be 0-100 if present
- `backlight_timeout_battery` must be > 0 if present
- Referenced profile IDs must exist

**Persistence**:
- Location: `~/.config/asus-linux-control/config.json`
- Format: JSON
- Auto-save on changes with 1-second debounce

---

### 7. TDP Configuration

**Description**: CPU TDP (power limits) and thermal ceiling snapshot, read from hardware sysfs attributes and optionally persisted in user config.

**Attributes**:
- `sustained_tdp_w`: integer (optional, 5–54W) - PL1/SPL power limit in watts; `null` if read failed or hardware unsupported
- `boost_tdp_w`: integer (optional, 5–54W) - PL2/SPPT power limit in watts; `null` if read failed
- `cpu_temp_limit_c`: integer (optional, 60–100°C) - Thermal throttle ceiling in degrees Celsius; `null` if read failed
- `is_supported`: boolean - Whether asus-nb-wmi PPT sysfs attributes are present (kernel 5.17+)

**Relationships**:
- Embedded optionally in Performance Profile (TDP override per profile)
- Embedded optionally in App Configuration (`tdp` key)

**Validation Rules**:
- `sustained_tdp_w` must be 5–54 if present
- `boost_tdp_w` must be 5–54 if present and must be >= `sustained_tdp_w`
- `cpu_temp_limit_c` must be 60–100 if present
- All validation enforced in Rust before sysfs write (constitution §I)

**Hardware Interface**:
- `/sys/devices/platform/asus-nb-wmi/ppt_pl1_spl` — reads/writes milliwatts (value × 1000)
- `/sys/devices/platform/asus-nb-wmi/ppt_pl2_sppt` — reads/writes milliwatts
- `/sys/devices/platform/asus-nb-wmi/ppt_cpu_limit` — reads/writes degrees Celsius directly

**Persistence Note**: TDP values are **volatile** — reset to firmware defaults on reboot. App re-applies on startup if config contains TDP values.

## Derived/Computed Values

These are calculated at runtime and not persisted:

### Current System State
- **Active Performance Mode**: Read from `/sys/class/platform/asus-nb-wmi/throttle_thermal_policy`
- **Current dGPU State**: Read from `/sys/class/platform/asus-nb-wmi/dgpu_disable`
- **Live Sensor Readings**: Generated from Sensor Reading entity every second

### Hardware Availability Status
- **Permission Status**: Whether user has write access to sysfs interfaces
- **Driver Status**: Whether asus-nb-wmi driver is loaded
- **Feature Availability**: Derived from Hardware Configuration

## Data Flow Diagrams

### Configuration Load/Save Flow
```
App Startup
  → Load config.json
  → Parse into App Configuration entity
  → Validate all referenced IDs
  → Apply default/last-used profile
  → Begin sensor monitoring
```

### Profile Application Flow
```
User selects Profile
  → Validate hardware supports all profile settings
  → Read Performance Profile entity
  → Apply thermal_policy to sysfs
  → Apply gpu_mode to sysfs
  → Load and apply Fan Curve if specified
  → Update UI state
  → Save last-used profile to config
```

### Sensor Monitoring Flow
```
Timer (1 Hz)
  → Create new Sensor Reading entity
  → Poll hwmon for temps/fans
  → Poll UPower for battery
  → Update UI with new reading
  → Discard reading (not persisted)
```

### Automation Trigger Flow
```
System Event (AC/battery change)
  → Query all enabled Automation Rules
  → Filter by matching trigger_condition
  → Sort by priority (ascending)
  → Apply first matching rule
  → Log automation action
```

## Entity Lifecycle

### Performance Profile
- **Created**: User creates custom profile or app loads presets
- **Stored**: Written to config.json immediately
- **Retrieved**: Loaded from config on app startup
- **Applied**: User selects profile → settings written to hardware
- **Deleted**: Removed from config.json (cannot delete if referenced by automation)

### Sensor Reading
- **Created**: Every 1 second by monitoring loop
- **Used**: Immediately displayed in UI
- **Expired**: Discarded after display (no persistence)

### Fan Curve
- **Created**: User defines custom curve or app loads presets
- **Validated**: Safety checks before allowing save
- **Stored**: Embedded in config.json
- **Applied**: When user selects curve or profile references it
- **Deleted**: Removed from config (cannot delete if referenced by profile)

### Automation Rule
- **Created**: User defines trigger → action mapping
- **Enabled**: Rule becomes active, monitoring for trigger
- **Triggered**: Condition met → action executed
- **Disabled**: Rule stops monitoring
- **Deleted**: Removed from config

## Validation Summary

| Entity | Key Validation | Enforcement Point |
|--------|----------------|-------------------|
| Performance Profile | thermal_policy in [0,1,2] | Backend before sysfs write |
| Sensor Reading | temps in [-50, 120]°C | Backend after hwmon read |
| Fan Curve | PWM >= 30% when temp > 80°C | Backend before curve save |
| Hardware Configuration | Read-only, no validation | Detection at startup |
| Automation Rule | No conflicting priorities | Backend before save |
| App Configuration | Valid JSON schema | Load/save with fallback |

## Implementation Notes

**Technology-Agnostic**: This model describes *what* data exists and *how* it relates, not *how* it's implemented in Rust structs or Dart classes.

**Serialization**: App Configuration serializes to JSON. Other entities exist only in-memory except when embedded in App Configuration.

**Concurrency**: Sensor Reading is the only entity with high-frequency updates (1 Hz). All other entities change on user action.

**Backwards Compatibility**: `version` field in App Configuration enables schema migration if data model evolves.
